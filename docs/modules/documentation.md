# Documentation（文档规划）模块架构

## 文档职责

本文是 Documentation 模块设计的唯一来源。它规定长期设计和当前开发计划的类型与位置、每个模块设计必须回答的问题，以及怎样检查这些结果。

本文保存跨版本稳定的文档安排；每个版本的目标、差距和阶段由当前开发计划负责。

## 架构定位与核心目标

Documentation 决定每份长期设计和当前开发计划放在哪里、由它单独说明什么，并为设计者、实现者和维护者提供统一入口。

> 每个模块都有一份能够独立指导实现的架构设计；维护者能够从统一入口找到全部长期设计，并从当前开发计划知道现阶段要完成什么、还差什么和从哪里继续。

Documentation 不参与产品运行，也不替其他模块作设计决定。

## 交付结果与职责边界

| 结果 | 使用者得到什么 |
| --- | --- |
| 文档位置与唯一来源 | 每类项目文档都有固定位置，每项目标、事实或状态只由一份文档负责 |
| 模块设计要求 | 每个模块设计都回答实现前必须确定的问题 |
| 文档导航 | 维护者从一个入口到达全部长期设计 |
| 当前计划位置与边界 | 维护者知道当前计划放在哪里、允许保留哪些内容 |
| 文档验证 | 缺失、重复或断开的文档关系能够被发现 |

Documentation 决定长期设计的名称、位置、引用方式和建立、修改、删除条件。它为当前开发计划固定位置和内容边界；[Development Planning](./development-planning.md) 负责计划的内容与生命周期。源码布局、项目检查和运行装配由负责这些结果的模块规划。

项目建立一个模块时，向 Documentation 提供稳定名称和一句明确的职责说明。Documentation 据此确定设计文档的位置和内容要求，模块设计者负责完成并维护设计。

## 文档结构与唯一来源

“唯一来源”是负责一项事实的文档。其他文档与它描述不一致时，以这份文档为准。

| 位置 | 唯一职责 |
| --- | --- |
| `README.md` | 作为仓库入口，指向使用、开发和文档入口 |
| `docs/README.md` | 把读者引向当前开发计划和全部长期设计，不在入口中重新定义内容 |
| `docs/design.md` | 规定产品结果、运行模块、公共契约、运行链路和全局保证 |
| `docs/development-plan.md` | 保存当前分支正在执行的版本计划，文件生命周期与该计划一致 |
| `docs/modules/documentation.md` | 规定文档类型、位置、事实的唯一来源和模块设计要求 |
| `docs/modules/<module-name>.md` | 规定一个模块的目标、交接结果、职责边界和验证要求 |

模块文档使用稳定的小写连字符文件名，例如 `cue-provider.md`。一个模块只有一份架构设计，系统设计是模块公共事实的唯一来源。

机器读取的语法、字段和配置值以对应的源代码或配置文件为准，文档只解释它们服务的目标和边界。

## 模块设计要求

每份模块设计必须让第一次接触该模块的维护者回答以下问题：

1. 这份文档独自负责哪些事实，什么变化要求更新它；
2. 模块为什么存在、交付什么结果、谁使用这个结果；
3. 模块接收什么，又交付什么；
4. 模块负责什么，相关职责由谁负责；
5. 模块依赖什么，哪些模块可以依赖它；
6. 成功、失败和边界情况分别产生什么结果；
7. 什么事实能够证明实现符合设计。

各模块可以按自己的特点安排章节，不必套用固定模板。其他模块依赖的数据结构或公共接口必须在实现前写清楚；只影响模块内部的做法由实现自行决定。

## 内容边界

模块设计用具体对象和动作直接描述确定的目标：谁接收什么、做什么、交付什么。术语第一次出现时说明它指什么；只有原文更便于识别或检索时才保留英文名称。

安全、权限、完整性和不可逆结果所需的限制必须明确写出。

长期设计只保存已经确认的目标、职责、机制、边界和验证要求。

当前开发计划保存当前交付目标的引用、尚未完成的差距、剩余阶段和下一行动入口。阶段完成后，代码、设计、配置或测试接管结果，计划继续维护剩余工作。

设计定义目标，实现与设计的差异进入当前开发计划。目标需要改变时，先确认新的结果和边界，再更新负责这些事实的设计与实现。

### 系统设计更新门槛

模块调查、设计或实现产生新信息时，先把新信息与当前系统设计逐项比较。只有以下至少一项发生变化，才修改 `docs/design.md`：

1. 用户可观察的产品结果、失败结果或全局保证改变；
2. 模块职责、结果所有者或依赖方向改变；
3. 模块间交接数据的业务含义、调用方必须提供的输入、调用方必须处理的结果分类或完整性保证改变。

以下内容只是在已有边界内确定做法，不构成系统设计变化：

- 为已有职责选择外部 SDK 事件或 API；
- 确定模块内部的算法、状态、标识、缓存、取消或校验机制；
- 在调用方依赖的业务含义和行为不变时，选择字段名、编码或序列化形式；
- 在系统设计没有承诺具体表示时，选择工具名称、消息格式或文件拆分；
- 增加证明已有目标和保证的验证方法。

修改 `docs/design.md` 前，先在变更说明中写清修改前的承诺、修改后的承诺，以及哪个调用方必须改变。缺少其中任何一项时，系统设计保持不变；新信息写入负责该机制的模块设计、实现、配置或验证。

## 建立、修改与删除

```text
项目确认一项独立模块职责
  → 在 docs/modules/ 建立唯一设计文档
  → 明确目标、交接结果、边界和验证要求
  → docs/README.md 链接到该文档
  → 根据设计开始实现
```

当前计划由 [Development Planning](./development-planning.md) 维护，版本历史统一由 Git 保存。
模块目标、公共结果或职责边界改变时，更新负责这些事实的设计、相关引用和实现；模块内部做法由对应实现维护。

模块停止交付当前结果时，同时删除模块实现、验证、设计文档和相关引用；这些变化的历史统一由 Git 保存。

## 验证与演进

自动检查确认：

- 文档入口指向的文件存在；
- 当前开发计划与指向它的文档入口同时存在或同时删除；
- 每份长期设计都能从 `docs/README.md` 到达；
- 每个模块只有一份架构设计；
- 相对链接有效。

文档审查确认：

- 模块设计回答规定的七个问题；
- 每项架构事实只由一份文档负责；
- `docs/design.md` 的每项修改都在变更说明中写清修改前的承诺、修改后的承诺和必须改变的调用方，并满足系统设计更新门槛；
- 长期设计只描述目标状态；
- 当前开发计划只保留正在执行的目标、剩余差距和下一行动入口；
- 第一次接触项目的维护者能够理解其中的对象、动作和结果。

验证失败时，本次变更尚未完成。结果必须指出具体文档和未满足的规则；文档失败不改变产品运行行为。

检查方法属于 Documentation 内部实现。只有文档系统交付的结果、事实的唯一来源或模块设计要求发生变化时，才修改本文。

新增一种长期文档前，必须同时确认：

1. 当前读者需要一种现有文档无法交付的结果；
2. 新文档负责一类现有文档没有负责的事实；
3. 读者能够从文档入口找到它，并持续验证其有效性。
