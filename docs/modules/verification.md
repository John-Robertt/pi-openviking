# Verification（验证）模块架构

## 文档职责

本文是 Verification 模块设计的唯一来源。它规定项目需要证明哪些事实、使用哪一层检查、检查结果怎样分类，以及什么结果表示一次变更已经完成。

本文直接描述项目采用的验证方式，不记录测试迁移、工具选择过程或单次运行结果。

## 架构定位、交付结果与职责边界

Verification 把系统设计和模块设计中的目标变成其他人也能重复运行的检查。模块实现者用实际结果判断代码是否达到设计要求，维护者运行同样的检查来判断一次变更是否完整。

> 每项当前行为、调用方依赖的接口和结果、重要失败方式都有成本与风险相称的检查；没有通过时，维护者能够看到要证明的事实、实际结果和未通过原因。

| 结果 | 使用者得到什么 |
| --- | --- |
| 必要检查 | 每项受影响的事实都有对应检查 |
| 验证结果 | 每项检查都有状态、实际输出和未通过原因 |
| 完成结论 | 维护者能够判断本次变更是否满足交付条件 |

每个模块的设计决定什么行为正确，并说明需要证明的事实。Verification 决定检查层次、测试组织、稳定命令和结果解释；它不替功能模块定义正确行为。

[Project Structure](./project-structure.md) 规定 `test/` 的仓库位置、产物位置和源码导入边界，[Documentation](./documentation.md) 规定设计文档的验证要求。Verification 只维护项目验证的组织方式和完成标准。

## 验证层次、位置与命令

| 层次 | 证明的事实 | 位置 | 稳定命令 |
| --- | --- | --- | --- |
| 静态检查 | 文档、目录、导入、类型和配置满足确定规则 | 根配置和项目命令 | `npm test` |
| 模块行为 | 一个模块通过公共入口交付预期结果和失败行为 | `test/modules/<module-name>/` | `npm test` |
| 跨模块集成 | 多个模块按照公共契约组合后交付完整结果 | `test/integration/` | `npm test` |
| 真实 Pi | Pi 的生命周期、上下文、session 和工具行为符合设计 | `test/pi/` | `npm run test:pi` |

`npm run typecheck` 只检查 TypeScript 类型，不代表完整验证。

检查使用能够直接证明目标事实的最低层次。模块行为能够证明时不启动完整集成。“受控替身”是测试提供、结果可预测的本地实现；它能够证明内部逻辑时不访问外部服务。需要确认 Pi 外部行为时使用真实 Pi，不从模拟结果推断。

`npm test` 在完整仓库副本中运行，不需要用户凭证、外部网络或本机绝对路径。测试通过模块公共入口观察行为，因此模块内部调整不会迫使行为未变的测试跟着修改。

## 验证流程

```text
确定受影响的事实
  → 选择最低且足够的检查层次
  → 运行必要检查
  → 分类未通过结果
  → 根据完成条件作出结论
```

修复已知错误时，先用一项测试、一条日志或一次真实运行重复观察错误结果；修改后再次运行同一项检查，确认结果已经改变。新增行为时，检查与行为一起交付。

检查数量只覆盖当前风险。一个现有检查已经能够证明目标事实时复用它，不增加第二个证明同一事实的检查。

## 结果状态与原因分类

状态回答“检查得出了什么结论”：

| 状态 | 含义 |
| --- | --- |
| `passed` | 实际结果符合需要证明的事实 |
| `failed` | 实际结果与需要证明的事实冲突 |
| `blocked` | 检查没有运行或缺少条件，无法得出结论 |

原因分类回答“为什么没有通过”：

| 分类 | 判断依据 |
| --- | --- |
| 实现问题 | 本次代码没有交付设计要求 |
| 验证问题 | 测试、数据或检查规则没有正确表达目标事实 |
| 环境问题 | 依赖、权限、凭证或运行环境不满足检查条件 |
| 不稳定检查 | 相同代码和条件重复运行得到不同结果 |
| 已有问题 | 修改前的运行结果表明失败已经存在，并且本次变更没有影响它 |

`failed` 和 `blocked` 都必须说明原因。环境无法满足检查条件时通常返回 `blocked`；不稳定检查由重复运行确认，已有问题由修改前的运行结果确认。

分类必须来自实际运行结果。不能确认原因时，继续运行能够区分这些分类的检查，不提前选择一个解释。

本次变更造成且属于当前范围的实现问题和验证问题必须解决。环境问题、不稳定检查和已有问题保留实际输出并报告影响；不能通过放宽断言或删除检查，把失败改成通过。

## 完成条件与依赖

一次变更完成时同时满足：

1. 每项受影响的事实都有检查；
2. 所有必要的自动检查返回 `passed`，所有必要的文档和结构审查确认符合设计；
3. 所有未通过结果都已分类，没有把 `blocked` 当作通过；
4. 被删除行为对应的测试、数据和辅助代码已经清理。

验证失败时，本次变更尚未完成。Verification 只报告要证明的事实、实际输出和原因分类，不改变产品运行行为。

Verification 遵守以下依赖边界：

1. 从项目的[系统设计](../design.md)和各模块设计中读取需要证明的结果。代码已经怎样运行，不能代替设计定义什么结果正确。
2. 测试代码通过源码模块的公共入口观察行为，其他路径规则由 [Project Structure](./project-structure.md) 负责。
3. 本地自动检查可以读取源码、配置和文档，但不能依赖真实用户数据、用户凭证或外部网络。
4. 测试框架、替身方案和检查工具属于 Verification 内部实现，不进入功能模块公共接口。

## 演进规则

只有验证层次、稳定命令、结果状态、原因分类或变更完成条件发生变化时，才修改本文。测试框架、测试文件拆分和检查工具没有改变这些结果时，由 Verification 实现自行调整。

新增一种验证层次前，必须同时确认：

1. 当前事实无法由现有层次直接证明；
2. 新层次交付一种独立且当前需要的检查结果；
3. 它的输入、结果和失败方式能够明确说明；
4. 它的成本与需要覆盖的风险相称。
