# Development Planning（开发规划）模块架构

## 文档职责

本文是 Development Planning 模块设计的唯一来源。它规定怎样从确定的目标和实际差距建立当前开发计划、怎样安排剩余阶段，以及计划怎样更新和结束。

本文保存跨版本稳定的规划规则；每个版本的目标、差距和阶段由当前开发计划负责。

## 架构定位、交付结果与职责边界

Development Planning 连接目标设计与开发行动。它把当前仍未实现的目标整理成有顺序、有完成条件的剩余工作，让维护者能够从一个明确入口开始，并在满足设计后结束。

> 当前计划只保留仍需行动的内容：目标来自系统设计或对应模块设计，差距来自代码、配置、测试和实际运行结果，每个阶段都交付能够检查的结果。

| 结果 | 使用者得到什么 |
| --- | --- |
| 当前开发计划 | 当前交付目标、范围、剩余差距和完成条件 |
| 阶段顺序 | 每个剩余阶段的前置条件、交付结果和先后关系 |
| 行动入口 | 当前阶段和下一项能够执行的动作 |

系统设计和模块设计决定要交付什么；Development Planning 决定在当前差距下先完成什么、后完成什么；各模块实现者决定内部算法并执行计划中的开发工作。

[Documentation](./documentation.md) 决定计划文档的位置和文档边界，[Project Structure](./project-structure.md) 决定代码与产物的位置，[Verification](./verification.md) 决定检查方式和变更完成条件。这三份设计分别是对应规则的唯一来源，Development Planning 据此安排工作。

## 计划输入与当前计划

Development Planning 使用三类输入：

1. 系统设计和模块设计给出的目标、边界与公共结果；
2. 代码、配置、测试和实际运行结果表明的当前实现；
3. 当前分支要完成的版本目标和已经确认的工作范围。

设计说明应当交付什么，代码、配置、测试和实际运行结果说明已经做到什么；两者的差异形成计划中的剩余差距。

每个分支最多有一份当前开发计划，固定位置是 `docs/development-plan.md`。计划随仓库提交，使另一位维护者取得完整仓库后能够从同一入口继续。

当前计划只包含：

- 当前交付目标及对应的系统设计或模块设计链接；
- 本次范围和明确不做的内容；
- 有文件、检查或实际运行结果支持的剩余差距；
- 按依赖关系排列的剩余阶段；
- 当前阶段、下一行动入口和仍然有效的阻塞项；
- 指向 Verification 完成条件的检查要求。

架构契约、文件位置和验证命令分别由负责它们的设计维护。计划只维护仍需行动的内容；完成结果由代码、设计、配置或测试继续说明，计划变更由 Git 保存。

## 建立计划与安排阶段

建立计划前同时满足：

1. 当前交付目标和范围已经确认；
2. 负责目标的设计能够直接指导实现；
3. 当前实现与目标之间的差距已经由文件、检查或实际运行结果确认；
4. 阶段之间的依赖关系能够说明；
5. 第一阶段有可以执行的入口，每个阶段有明确的交付结果和检查要求。

每个阶段只解决一组相互依赖的差距，并写清前置条件、范围、交付结果和验证要求。阶段按依赖关系排列；相互独立的工作可以并行，后续阶段在前置结果交付后开始。

当前最阻碍交付目标、并且已经具备行动条件的阶段是当前阶段。Development Planning 固定阶段必须交付的结果和进入下一阶段的条件，模块实现者自行选择内部编码步骤。

## 更新计划

每个阶段完成后，用 Verification 规定的检查确认交付结果。结果符合预期时，从计划中删除已经完成的步骤，由代码、设计、配置或测试继续记录结果；随后根据剩余差距确定新的当前阶段和下一行动入口。

结果与预期不一致时，重新检查实际状态，并据此更新差距、阶段顺序和下一行动。计划中的原因解释必须由实际结果支持。

遇到阻塞时，计划保留缺少的条件、它阻止的结果和下一项能够解除阻塞的行动。结果为 `blocked` 的阶段仍未完成；检查状态和原因分类由 Verification 负责。

目标需要改变时，先停止受影响的阶段。负责目标的设计先写明新的结果和边界，计划再据此更新受影响的内容。

## 完成条件与生命周期

当前计划完成时同时满足：

1. 当前交付目标要求的结果已经实现；
2. Verification 规定的必要检查全部满足完成条件；
3. 全部剩余差距已经由各阶段解决，阻塞项已经解除；
4. 本次工作替代的实现、测试、配置、文档和临时内容已经清理；
5. 当前结果分别由代码、设计、配置或测试继续记录，每项结果只有一个负责来源。

存在下一项已经确认的版本目标时，`docs/development-plan.md` 直接改为新的当前计划；没有下一项当前目标时删除该文件和指向它的导航。Git 是版本计划历史的唯一来源。

Development Planning 在开发过程中读取设计与实际结果，并把当前计划写入 `docs/`；产品运行模块继续按照系统设计中的依赖关系工作。

规划审查确认：

- 当前计划只存在于 Documentation 规定的位置；
- 每项目标都链接到系统设计或对应模块设计，每项差距都有文件、检查或实际运行结果支持；
- 当前阶段的前置条件已经满足，下一行动能够直接执行；
- 计划中的每项内容都对应当前目标或剩余差距；
- 计划只在 Verification 的完成条件满足后结束。

## 演进规则

本文随计划的输入、交付内容、阶段边界、更新方式或完成条件变化。具体版本的目标、差距、阶段和进度由当前计划维护。

新增一种计划内容前，必须同时确认：

1. 它影响当前阶段、下一行动或完成判断；
2. 现有计划内容不能表达这项需要；
3. 它有明确来源，并且能够随差距消失而从计划中删除。
