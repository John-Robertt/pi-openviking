# Project Structure（项目结构）模块架构

## 文档职责

本文是 Project Structure 模块设计的唯一来源。它规定项目文件放在哪里、其他模块可以导入哪个文件、配置和产物放在哪里，以及怎样检查这些结果。

本文直接描述项目采用的目标结构，不记录目录迁移、实施步骤或临时位置。

## 架构定位、交付结果与职责边界

一个模块的职责确认后，Project Structure 为它确定代码、配置和测试的位置。模块实现者按这些位置写入文件，检查工具据此发现放错位置或导入错误的代码。

> 每个项目文件都有一个负责它的模块；每个源码模块都有稳定的公共入口；模块可以自由组织内部代码，不会侵入其他模块。

| 结果 | 使用者得到什么 |
| --- | --- |
| 仓库区域 | 代码、文档、测试、配置和本地产物各有固定位置 |
| 模块位置 | 每个源码模块有稳定目录和公共入口 |
| 跨模块导入规则 | 代码只导入系统设计允许的模块及其公共入口 |
| 结构验证 | 放错位置、直接导入其他模块内部文件和使用错误路径的代码能够被发现 |

[Documentation](./documentation.md) 决定 `docs/` 内部怎样组织。Project Structure 只保留文档区域，不重复文档类型和事实来源。

Project Structure 规定测试代码位于 `test/`；Verification 决定其中的组织方式、验证内容和执行方法。Project Structure 规定仓库级配置的位置；配置内容由使用它的工具或模块负责。Assembly 决定运行模块怎样组合。

Project Structure 不决定模块交付什么，也不设计模块内部的数据、算法和文件拆分。

## 仓库区域

| 位置 | 唯一职责 |
| --- | --- |
| `src/` | 保存产品运行代码和跨模块公共数据 |
| `test/` | 保存项目验证代码、测试数据和测试辅助代码 |
| `docs/` | 保存 Documentation 规划的项目文档 |
| `.dev/` | 保存本机开发、构建和单次运行产生的可删除内容 |
| 仓库根目录 | 保存项目入口、许可证和整个仓库共同使用的工具配置 |

仓库级工具要求固定文件位于根目录时，文件保留在根目录，例如 `package.json`、`package-lock.json` 和 `tsconfig.json`。只服务一个模块的文件放在该模块目录内。

密钥和访问凭证来自环境变量，不写入仓库。生成内容和单次运行产物留在被忽略的项目内目录，不写到项目外，也不提交。

目录随实际文件建立。没有文件就不创建目录，也不为尚未确认的模块预留空位置。

## 源码模块与公共入口

| 位置 | 唯一职责 |
| --- | --- |
| `src/index.ts` | Pi 扩展入口，在架构上属于 Pi Boundary |
| `src/contracts/` | 保存跨模块传递的公共数据，不保存具体模块实现 |
| `src/assembly/` | 保存 Assembly 实现 |
| `src/pi-boundary/` | 保存 Pi Boundary 实现 |
| `src/cue-provider/` | 保存 Cue Provider 实现 |
| `src/retriever/` | 保存 Retriever 实现 |
| `src/observation/` | 保存 Observation 实现 |

`src/index.ts` 除 Pi SDK 外，只导入 Assembly 和 Pi Boundary 的公共入口，不承载记忆业务。

“公共入口”是其他生产模块唯一可以导入的文件。源码模块使用与模块设计相同的小写连字符名称，并用目录中的 `index.ts` 作为公共入口；目录中的其他文件只供本模块使用。

公共入口只暴露调用方当前需要的接口、结果和创建方式。模块内部可以按自己的需要拆分文件和目录。

多个模块使用的代码仍然必须有一个负责模块。可复用代码放在负责其结果的模块中；没有模块能够负责时，先确认新的独立职责。

## 跨模块导入规则

[`docs/design.md`](../design.md) 决定一个运行模块可以调用哪些模块。Project Structure 把这个决定落实为以下源码导入规则：

1. 生产代码跨模块导入时，只能导入对方的 `index.ts`；
2. Assembly 可以导入所有模块的公共入口，不能导入模块内部文件；
3. `src/contracts/` 不导入运行模块，也不包含外部 SDK 类型；
4. Pi SDK 只出现在 `src/index.ts` 和 `src/pi-boundary/`；
5. 外部 SDK 只由使用它的模块导入，外部类型不能进入跨模块公共数据；
6. `src/` 不依赖 `test/`。

普通导入和 `import type` 都遵守这些规则。代码、配置和脚本使用仓库内的相对位置，不写入本机绝对路径，因此整个仓库复制到另一台机器后仍可工作。

## 模块建立与删除

模块设计确认稳定名称和交接结果后，有运行代码的模块建立 `src/<module-name>/index.ts`。专用配置放入模块目录，验证代码由 Verification 安排在 `test/` 内。模块在实现前声明需要导入哪些模块。

模块没有对应代码时，不建立源码目录。模块删除时，同时删除源码、专用配置、测试、入口引用和不再使用的依赖。

模块内部文件移动或拆分没有改变公共入口和系统依赖时，由模块自行决定。

## 验证与演进

自动检查确认：

- 仓库中的每个文件都位于前文规定的区域；
- 每个源码模块只有一个公共入口；
- 生产代码没有跨模块内部导入；
- 每条跨模块导入都指向系统设计允许的模块及其公共入口；
- 源码不依赖测试；
- 代码、配置和脚本没有本机绝对路径，仓库整体复制后仍可工作；
- 生成内容位于被忽略的项目内目录。

结构审查确认：

- 每个文件和公共入口都有当前使用者；
- 模块内部仍能自由组织实现；
- 共享代码有唯一负责模块；
- 新区域交付现有区域无法交付的独立结果。

结构验证失败时，本次变更尚未完成。结果必须指出具体文件、实际依赖和违反的规则；结构检查不改变产品运行行为。

只有仓库区域的职责、模块公共入口的位置、跨模块导入规则或模块建立方式发生变化时，才修改本文。模块内部文件、工具配置值和检查代码没有改变这些结果时，由负责它们的模块自行调整。

新增一个仓库区域前，必须同时确认：

1. 当前文件需要一种现有区域无法提供的归属；
2. 新区域有唯一职责、明确使用者和清楚的依赖方向；
3. 新区域的边界能够持续验证。
